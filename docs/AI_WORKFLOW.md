# AI_WORKFLOW — 岡大AIStudio公式Webサイト

本書はこのプロジェクトの**詳細実行手順の正本**。開始順序の唯一の正本は [AGENTS.md](../AGENTS.md)。汎用開発手順の採用版・差分もAGENTSに記す。

## 1. ゴールを決める
- サークルの公式Webサイトとして今回完成させる成果、利用者に見せる内容、完了条件、対象外、承認済み範囲を確認する。
- 質問・学習のみなら開発Issueは原則不要。決定済み事項は聞き直さない。

## 2. 現在地を最小限確認
- 関連する既存Issueの現行欄と直近コメント、対象コード、GitHub Actions、公開先の実設定を必要な範囲だけ照合する。
- 古い作業案や保留を自動再開しない。未確認、保留、真のブロッカーを区別する。
- 技術・CI・ホスティング・ドメイン・認証/DBの有無は未確定。存在を仮定して作業しない。

## 3. 設計と実装
- 画面・コンテンツ・アクセシビリティ、メンバー向け編集の範囲、必要なデータを検討し、変更対象と検証方法を定める。
- 通常の共同開発では作業ブランチ→PR→必要なレビュー→mainへ統合。ブランチ保護やレビュー必須設定が実際に存在するとは推定しない。
- 本人が明示的に認めた小さな初期設定等はmain直接更新も可能。ただし本番への自動連動が設定された後はその影響を先に確認。
- 安全な実装・修正・テスト・記録は可能な限り一括で進める。無関係なコードを変更しない。

## 4. テストとCI
- 必須CIは**未設定／未確認**。技術スタック決定後、実際のチェック（build・lint・typecheck・unit・E2E等）を確認してここに記す。
- CIがない間は、変更のリスクに応じてコード差分、文書リンク、ビルド可能ならローカルビルド、主要操作、スマホ表示等を検証する。
- 実行したものだけPASS/FAIL/NOT RUNと証拠を記録し、実行できない検証はNOT RUNと残リスクを明示する。

## 5. 検証と公開
- 検証用URL・本番URL・Vercel等の配備先は**未決定**。決定したら実環境のID・権限・デプロイ条件を照合して別途文書化する。
- 検証環境がある場合はその環境で受入。ない場合はローカル/プレビュー等で必要な代替確認をし、残る未確認を明示する。
- 公開・外部サービス設定・費用・組織権限・実データ変更は、対象操作・影響・復旧手順を含む責任者の明示承認後に行う。
- アプリの旧版への切戻しはデータ変更の巻き戻しと同義ではない。

## 6. Issue・実績
- 作業の独立した成果単位でIssueを作成。同一ゴールの調査、設計、実装、テスト、配備準備のために分割しない。
- 優先度はtaskのみP0〜P3。management/learningは原則「対象外」。
- 正本は関連Issueの現行欄。変更のコミットSHA、確認環境、PASS/FAIL/NOT RUN、未完了、次の担当・停止条件を記す。Issueのない単純な初期準備はコミット履歴で足りる。
- 完了条件を満たす場合だけClose。個人の学習計画をサイト開発のブロッカーにしない。

## 7. 作業の止め方と改善
- 未承認の公開、未知の警告、対象の不一致、データ損失リスクがあれば依存工程を停止。安全に独立した作業は進める。
- 本人による手動設定は場所・順序・正常/異常時の分岐・復旧条件・報告項目をまとめて案内する。
- 汎用化できる実際の改善だけ [development-workflow](https://github.com/kanata-projects/development-workflow) に提案。共通版の更新をこのリポジトリへ自動適用しない。
